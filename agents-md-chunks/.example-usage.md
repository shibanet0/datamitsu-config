# AGENTS.md Usage Examples

Pick one of the variants below depending on your project type. The reference line is intentionally a single binding statement — do not split it, do not soften it, do not move it below project content.

## Choosing a variant

The question that separates the two documentation variants is whether the documentation is
**published**, not whether it exists.

| Variant                   | Pick it when                                                                                          | Documentation lives in                                                          | README                                                     |
| ------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `agents-base.md`          | Private project, or public without documentation obligations                                          | —                                                                               | —                                                          |
| `agents-docs-markdown.md` | Documentation is Markdown files read in the repository; nothing builds a site from them               | `docs/`                                                                         | The entry point; may carry more detail                     |
| `agents-docs-website.md`  | Documentation is published as a site built from the repository (a static site generator, a docs host) | `website/` (the generator's content directory); `docs/` keeps unpublished notes | Minimal: what it is, install, a minimal example, site link |

A project that starts building a site from its Markdown moves to the website variant: the pages go
to `website/`, `docs/` keeps what must not be published (`docs/backlog/`, `docs/plans/`), and the
README shrinks to the four items above. Both documentation variants open with a line saying which
kind of project they are for, so an agent working under the wrong one can notice and say so.

## Project with rule overrides

To override specific rules from the shared file, place the override statements **above** the reference line. They must be explicit, granular, and named. Anything not explicitly overridden remains in full effect.

Example — a fork of an upstream open-source project that mandates its own commit message format. The fork must follow upstream conventions to keep patches mergeable, but everything else from the shared rules still applies:

```markdown
# AGENTS.md

**Commit messages in this repository follow the upstream project's commit format documented in `CONTRIBUTING-upstream.md`, not Conventional Commits. This override applies only to commit messages; branch naming, PR descriptions, and all other workflow rules remain unchanged.**

**Read [.datamitsu/ai/agents/agents-base.md](.datamitsu/ai/agents/agents-base.md) now and follow it strictly without asking permission. Any instructions above this line in this file override matching rules in that document; everything else in that document is binding.**

## Project Overview

<!-- Project-specific content here -->
```

### Override rules

- Override statements live in the first lines of `AGENTS.md`, before the reference line. Never below it, never in a separate section.
- Each override is a single explicit statement naming exactly what is changed. No general phrases like "rules are relaxed" or "use your judgment".
- Overrides are granular. Override the commit format without touching the test isolation rules. Override the documentation surface without touching the language policy.
- If multiple overrides are needed, write them as separate consecutive statements, one per paragraph.
